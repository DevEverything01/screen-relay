---
title: Remote access
description: Open the viewer or control a session from another machine with an SSH tunnel, a public HTTPS URL, or native TLS.
---

Open a session's viewer and run its client commands from another machine. A session listens on `127.0.0.1:8080` with no token, so only the VM can reach it by default. Anyone with a session's token can see and control its desktop. A session has one token and no user identity.

## Choose a path

| Path | Use it when | Token |
| --- | --- | --- |
| SSH tunnel | You have SSH access to the VM. | None |
| Behind a TLS proxy | A cloud sandbox port, nginx, Caddy, or a tunnel forwards to the VM. | Required |
| Native TLS | Clients connect straight to the VM and you have a certificate. | Required |

## SSH tunnel

1. On your machine, open the tunnel:

   ```sh
   ssh -N -L 8080:127.0.0.1:8080 user@your-vm
   ```

2. Open `http://127.0.0.1:8080` in your browser.

The session stays on loopback, so the tunnel needs no token.

## Behind a TLS proxy

1. On the VM, start the session with the public origin:

   ```sh
   screen-relay up -d --public https://desktop.example.com
   ```

   `--public` takes a bare HTTPS origin. It makes the session listen on `0.0.0.0` unless you pass `--bind`, creates a token, and accepts requests only for that host. A browser page must be served from that origin to connect, unless you list its origin with [`--allow-origin`](#browser-origins).

2. Configure the proxy to:
   - forward every path with no prefix, including `/viewer.js`, `/stream`, and `/control` ([endpoints](/docs/protocol#endpoints))
   - forward WebSocket upgrades over HTTP/1.1
   - pass `Host`, `Origin`, and `Authorization` through unchanged, and keep the WebSocket subprotocol header
   - keep `Authorization` and the subprotocol header out of its logs, because the token travels in both

3. Open the viewer link that `up` printed.

Without `--tls-cert`, the engine serves plain HTTP and the proxy ends TLS. The proxy must be the only thing that can reach the port. The engine ignores `X-Forwarded-*` headers.

`up` prints a `TLS proxy` row that names the forwarding target.

## Native TLS

1. On the VM, start the session with your certificate:

   ```sh
   screen-relay up -d --tls-cert fullchain.pem --tls-key key.pem --public https://desktop.example.com
   ```

2. Open the viewer link that `up` printed.

The engine serves HTTPS itself, prints no `TLS proxy` row, and speaks HTTP/1.1 only. Client commands on the VM accept the session's own certificate even when its host name does not match, so a self-signed certificate works there.

## Browser origins

A browser adds an `Origin` header to WebSocket connections and to cross-origin requests, naming the page that made them. The engine checks that header in addition to the token, so a page on another site cannot use a token it obtained.

| Session | Origins the engine accepts |
| --- | --- |
| Started with `--public` | The `--public` origin, each origin in `--allow-origin`, and a matching loopback origin for direct local connections. |
| Started without `--public` | Loopback origins (`http` or `https`, `localhost` or `127.0.0.1`, any port), and each origin in `--allow-origin`. |

A request from any other origin gets 403 `forbidden`, and a WebSocket fails its handshake. The CLI, the Node SDK, and other clients that send no `Origin` header are not affected.

To let a page on another origin connect, such as an app that embeds the viewer, list its origin when you start the session:

```sh
screen-relay up -d --public https://desktop.example.com --allow-origin https://app.example.com
```

- Separate several origins with commas and no spaces, up to 16. You can set `SCREEN_RELAY_ALLOW_ORIGIN` instead of the flag.
- Write each origin the way the browser sends it: lowercase `https://HOST` or `https://HOST:PORT`, with no path and no trailing slash. Leave out port 443.
- The engine compares the whole string. It has no wildcard, so `https://app.example.com` does not cover `https://www.app.example.com`.
- `--allow-origin` creates a token even when the session listens on `127.0.0.1`, and the allowed page must send it.
- The engine never accepts `Origin: null`, which a browser sends from a sandboxed frame or a `file://` page.

### Update an app that connects from another origin

Earlier versions accepted any origin when the session had a token. After upgrading, a session with `--public` also refuses the viewer opened at `http://127.0.0.1:8080` or through an SSH tunnel, because that page's origin is not the `--public` origin. Open the `--public` URL instead.

An app that opens `/stream` or calls the HTTP API from its own origin now gets 403 until you allow that origin. This includes an MCP App that renders the viewer inside an AI client:

1. Find the origin the app's page runs on. In the browser's or client's developer tools, open the failed `/stream` request and read its `Origin` request header.
2. Restart the session with that value in `--allow-origin`. Restarting creates a new token, so give the app the new one.
3. Reload the app.

If the header is `null`, the client renders the app in a frame without an origin of its own, and the app cannot connect from the browser. Route its requests through a server you control, which sends no `Origin` header and holds the token.

## Tokens

screen-relay creates a 64-character lowercase hex token (256 random bits) whenever the session listens anywhere other than `127.0.0.1`, or uses `--public` or `--allow-origin`.

- The token is stored in a `token` file in the session's state directory, readable only by its owner. `screen-relay status --json` shows the path as `tokenFile`.
- `screen-relay status` hides the token unless you pass `--show-token`.
- The viewer reads `#token=` from the link that `up` prints, removes it from the address bar, and uses it only on `https://` or loopback pages. Browsers never send the fragment to the server.
- Each `screen-relay up` creates a new token and ends open connections. To rotate a token, run `screen-relay down`, then `screen-relay up`.
- To give a custom client access that works only once, request a ticket with `POST /tickets` and the token. The client opens its WebSocket with the `ticket.TICKET` subprotocol instead of the token, and the ticket stops working after that connection or after 60 seconds. The bundled viewer doesn't accept tickets yet; it still needs the `#token=` link. See the [protocol](https://github.com/vercel-labs/screen-relay/blob/main/PROTOCOL.md).

## Control a session from your laptop

1. On your laptop, install the CLI. It needs Node 22 or newer and runs on any OS:

   ```sh
   npm install -g screen-relay
   ```

2. On the VM, run `screen-relay status --show-token`, and copy the token into a file named `token` on your laptop.

3. Set the target once per shell, then run client commands:

   ```sh
   export SCREEN_RELAY_URL=https://desktop.example.com
   export SCREEN_RELAY_TOKEN_FILE=./token
   screen-relay status
   screen-relay screenshot screen.png
   ```

To pass the URL and token per command, use `--url` and `--token-file` instead. Use HTTPS for any remote host. Plain HTTP works only for `localhost` or `127.0.0.1`, and redirects are not followed. The [CLI reference](/docs/cli#client-target) lists the URL rules. In Node, pass the same URL and token to `createClient` ([SDK options](/docs/sdk#options)).

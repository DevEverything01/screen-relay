---
title: Remote access
description: Open the viewer or control a session from another machine with an SSH tunnel, a public HTTPS URL, or native TLS.
---

Open a session's viewer and run its client commands from another machine. A session listens on `127.0.0.1:8080` by default, including when you pass `--public`. It stays on loopback unless you pass `--bind`, so a proxy or client that connects without a tunnel needs an address it can reach. Anyone with a session's token can see and control its desktop. A session has one token and no user identity.

## Choose a path

| Path | Use it when | Listen address | Token |
| --- | --- | --- | --- |
| SSH tunnel | You have SSH access to the VM. | `127.0.0.1` (default) | None on Linux; required on macOS and Windows |
| Behind a TLS proxy | A cloud sandbox port, nginx, Caddy, or a tunnel forwards to the VM. | `127.0.0.1` for a proxy on the VM; otherwise an address the proxy can use | Required |
| Native TLS | Clients connect straight to the VM and you have a certificate. | An address clients can use, such as the VM's public address | Required |

## SSH tunnel

1. On your machine, open the tunnel:

   ```sh
   ssh -N -L 8080:127.0.0.1:8080 user@your-vm
   ```

2. Open `http://127.0.0.1:8080`, or the viewer link that `up` printed when the session has a token.

The session stays on loopback, so the tunnel reaches it without a public URL. Linux sessions need no token; macOS and Windows sessions always have one.

## Behind a TLS proxy

1. On the VM, start the session with the public origin:

   ```sh
   screen-relay up -d --public https://desktop.example.com
   ```

   `--public` takes a bare HTTPS origin, sets the accepted public host, and creates a token. It does not change the listen address. Pages and apps on any origin can connect when they send the token.

2. Configure the proxy to:
   - forward every path with no prefix, including `/viewer.js`, `/stream`, and `/control` ([endpoints](/docs/protocol#endpoints))
   - forward WebSocket upgrades over HTTP/1.1
   - pass `Host`, `Origin`, and `Authorization` through unchanged, and keep the WebSocket subprotocol header
   - keep `Authorization` and the subprotocol header out of its logs, because the token travels in both

3. Open the viewer link that `up` printed.

Without `--tls-cert`, the engine serves plain HTTP and the proxy terminates TLS. A proxy on the same VM can use `127.0.0.1`. For a proxy that runs elsewhere, pass `--bind` with an address only the proxy can reach. Do not expose that port to clients. The engine ignores `X-Forwarded-*` headers.

`up` prints a `TLS proxy` row that names the forwarding target.

## Native TLS

1. On the VM, start the session with your certificate:

   ```sh
   screen-relay up -d --bind 0.0.0.0 --tls-cert fullchain.pem --tls-key key.pem --public https://desktop.example.com
   ```

2. Open the viewer link that `up` printed.

The engine serves HTTPS itself, prints no `TLS proxy` row, and speaks HTTP/1.1 only. This example listens on all IPv4 interfaces. Pass a specific address to `--bind` if only one interface should accept connections. Client commands on the VM accept the session's own certificate even when its host name does not match, so a self-signed certificate works there.

## Tokens

screen-relay creates a 64-character lowercase hex token (256 random bits) whenever the session listens anywhere other than `127.0.0.1`, uses `--public`, or runs on macOS or Windows.

- The token is stored in a `token` file in the session's state directory, readable only by its owner. `screen-relay status --json` shows the path as `tokenFile`.
- `screen-relay status` hides the token unless you pass `--show-token`.
- The viewer reads `#token=` from the link that `up` prints, removes it from the address bar, and uses it only on `https://` or loopback pages. Browsers never send the fragment to the server.
- Each `screen-relay up` creates a new token and ends open connections. To rotate a token, run `screen-relay down`, then `screen-relay up`.
- To give a custom client access that works only once, request a ticket with `POST /tickets` and the token. The client opens its WebSocket with the `ticket.TICKET` subprotocol instead of the token, and the ticket stops working after that connection or after 60 seconds. The bundled viewer doesn't accept tickets yet; it still needs the `#token=` link. See the [protocol](https://github.com/vercel-labs/screen-relay/blob/main/PROTOCOL.md).

## Control a session from your laptop

1. On your laptop, install the CLI. It needs Node 22 or newer and runs on any OS:

   ```sh
   npm install -g screen-relay
   ```

2. On the VM, run `screen-relay status --show-token`, and copy the token into a file named `token` on your laptop.

3. Set the target once per shell, then run client commands:

   ```sh
   export SCREEN_RELAY_URL=https://desktop.example.com
   export SCREEN_RELAY_TOKEN_FILE=./token
   screen-relay status
   screen-relay screenshot screen.png
   ```

To pass the URL and token per command, use `--url` and `--token-file` instead. Use HTTPS for any remote host. Plain HTTP works only for `localhost` or `127.0.0.1`, and redirects are not followed. The [CLI reference](/docs/cli#client-target) lists the URL rules. In Node, pass the same URL and token to `createClient` ([SDK options](/docs/sdk#options)).

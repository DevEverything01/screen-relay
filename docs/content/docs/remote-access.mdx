---
title: Remote access
description: Open the viewer or control a session from another machine with an SSH tunnel, a public HTTPS URL, or native TLS.
---

A session listens on `127.0.0.1:8080` with no token, so only the VM can reach it. To open the viewer or run client commands from another machine, follow one of the paths below. Anyone with a session's token can see and control its desktop. There is one token per session and no user identity.

## Choose a path

| Path | Use it when | Token |
| --- | --- | --- |
| SSH tunnel | You have SSH access to the VM. | None |
| Behind a TLS proxy | A cloud sandbox port, nginx, Caddy, or a tunnel forwards to the VM. | Required |
| Native TLS | Clients connect straight to the VM and you have a certificate. | Required |

## SSH tunnel

Run this on your machine:

```sh
ssh -N -L 8080:127.0.0.1:8080 user@your-vm
```

Open `http://127.0.0.1:8080`. The session stays on loopback, so nothing needs a token.

## Behind a TLS proxy

```sh
relay up -d --public https://desktop.example.com
```

`--public` takes a bare HTTPS origin. It makes the session listen on `0.0.0.0` unless you pass `--bind`, creates a token, and accepts requests only for that origin. `up` prints a `TLS proxy` row naming the forwarding target.

Without `--tls-cert` the engine serves plain HTTP and the proxy ends TLS, so the proxy must be the only thing that can reach the port. It must:

- forward every path with no prefix, including `/viewer.js`, `/stream`, and `/control` ([endpoints](/docs/protocol#endpoints))
- forward WebSocket upgrades over HTTP/1.1
- pass `Host`, `Origin`, and `Authorization` through unchanged, and keep the WebSocket subprotocol header
- keep `Authorization` and the subprotocol header out of its logs, because the token travels in both

The engine ignores `X-Forwarded-*` headers.

## Native TLS

```sh
relay up -d --tls-cert fullchain.pem --tls-key key.pem --public https://desktop.example.com
```

The engine serves HTTPS itself, prints no `TLS proxy` row, and speaks HTTP/1.1 only. Use a certificate your clients trust with the public URL's hostname. Client commands on the VM accept the session's own certificate without a hostname check, so a self-signed one works there.

## Tokens

Relay creates a 64-character lowercase hex token (256 random bits) whenever the session listens anywhere other than `127.0.0.1` or uses `--public`.

- Relay stores the token in a `token` file in the session's state directory, readable only by its owner. `relay status --json` shows the path as `tokenFile`.
- `relay status` hides the token unless you pass `--show-token`.
- The viewer reads `#token=` from the link that `up` prints, removes it from the address bar, and uses it only on `https://` or loopback pages. Browsers never send the fragment to the server.
- Each `relay up` creates a new token and ends open connections. To rotate one, run `relay down` then `relay up`.

## Control a session from your laptop

Install the CLI alone with `./install.sh --client-only` (any OS with Node 26 or newer). Copy the token from `relay status --show-token` into a file, then set the target once per shell:

```sh
export RELAY_URL=https://desktop.example.com
export RELAY_TOKEN_FILE=./token
relay status
relay screenshot screen.png
```

Pass `--url` and `--token-file` per command instead. Use HTTPS for any remote host; plain HTTP works only for `localhost` or `127.0.0.1`, and redirects are not followed. The [CLI reference](/docs/cli#client-target) has the URL rules, and in Node you pass the same URL and token to `createClient` ([SDK options](/docs/sdk#options)).

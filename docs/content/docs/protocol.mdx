Use the HTTP API to read the desktop state, take screenshots, and send input from any language.

## Quick start

### Read the screen

Start a session, then run these commands on the VM or through an [SSH tunnel](/docs/remote-access#ssh-tunnel). They use the default address; use your HTTPS origin if the session uses TLS.

On the VM, `relay status --json` shows the `tokenFile` path; replace `/path/to/token` with it. A session bound to `127.0.0.1` without `--public` has no token, so omit the `TOKEN` line and the `Authorization` headers.

```sh
TOKEN="$(cat /path/to/token)"

curl -fsS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/capabilities
curl -fsS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/screenshot.png -o screen.png
```

The screenshot is saved as `screen.png`.

### Send input

Only one client can control input at a time, so close the viewer before sending input.

Input uses 16-byte binary records. The easiest way to send input is with the [CLI](/docs/cli) or [Node SDK](/docs/sdk). To click the center from another machine, copy the token file securely and replace the example URL and path:

```sh
relay click 0.5 0.5 --url https://desktop.example.com --token-file ./token
```

For a local session, omit `--url` and `--token-file`. For other languages, see [Input records](#input-records).

## Endpoints

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | <span id="get-capabilities" />`/capabilities` | Returns the desktop size, backend, features, and input limits as JSON. |
| `GET` | `/screenshot.png` | Returns a fresh PNG without the cursor, even when another client owns input. |
| `POST` | <span id="post-input" />`/input` | Sends a batch of binary input records. |
| `GET` | <span id="get-metrics" />`/metrics` | Returns stream and resource metrics as JSON. |
| `GET` | `/`, `/index.html`, `/viewer.js` | Serves the viewer. |
| WebSocket | `/stream` | Streams video, sends cursor images when supported, and accepts viewer input. |
| WebSocket | `/control` | Sends input and receives a response for each event, without video. |

## Authentication

Send `Authorization: Bearer TOKEN` with HTTP requests when the session has a token. WebSocket clients offer `nsl1` and `bearer.TOKEN` as subprotocols; the server selects `nsl1`. Do not put the token in a request URL. See [Tokens](/docs/remote-access#tokens).

| Header | Rule |
| --- | --- |
| `Host` | Use `localhost` or `127.0.0.1` with an optional port, or the exact authority configured with `--public`. |
| `Origin` | Optional for HTTP and `/control`, required for `/stream`. If sent, it must be a loopback origin with a loopback host, or the exact `--public` origin with a token configured. |

## Input records

<span id="input-events" />

`POST /input` accepts 1 to 256 consecutive 16-byte records, not JSON. Send `Content-Length` and omit the 20-byte WebSocket header. All multibyte fields are big-endian. Set unused fields to zero.

| Offset | Size | Field | Value |
| ---: | ---: | --- | --- |
| 0 | 1 byte | Type | Event type from the table below. |
| 1 | 1 byte | Reserved | Zero. |
| 2 | 2 bytes | Code | Key, button, or wheel axis. |
| 4 | 4 bytes | Value | Signed wheel delta or Unicode scalar. |
| 8, 10 | 2 bytes each | X, Y | Coordinates from 0 to 65535 across the desktop. |
| 12 | 2 bytes | Button mask | Low 5 bits only. |
| 14 | 2 bytes | Modifier mask | Low 8 bits only. |

| Type | Event | Fields |
| ---: | --- | --- |
| 1, 2 | Key down, key up | Code is a HID usage from 0 to 231. Keys are physical; the desktop layout determines the character. |
| 3 | Pointer move | X and Y are the target position. |
| 4, 5 | Button down, button up | Code is 1 to 3; X and Y are the target position. |
| 6 | Wheel | Code is 0 for vertical or 1 for horizontal; value is a multiple of 120 from -1200 to 1200. X and Y are the target position. |
| 7 | Release all | Code, value, and both masks must be zero. |
| 8 | <span id="text-events" />Text | Value is one Unicode scalar from 1 to `0x10FFFF`, excluding `0xD800` to `0xDFFF`. Code and both masks must be zero. |

Text events type a character without changing held keys. Held modifiers are lifted and restored around the character. Values `0x0A` and `0x09` type Return and Tab. X11 uses up to 16 spare keys for characters absent from the layout; Wayland uses up to 32. On X11, those characters can be missed if an application freezes for over 50 ms and spare keys are reused. If no spare key is available, the event is unsupported.

Events run in order and stop at the first failure. A successful response reports the number of records applied, for example `{"applied":1}`. The response waits for the desktop to apply them; it does not guarantee the application reacted. Keys and buttons held by a batch are released when it ends or fails. Masks do not press or release keys or buttons: send explicit down and up events.

## Errors and limits

<span id="limits" />

| Status or limit | Meaning and action |
| --- | --- |
| 400 `invalid_input` | The body is empty, not a multiple of 16 bytes, or has an invalid record. `index`, when present, is the zero-based index of the failed record. |
| 401 `unauthorized` | Send the correct session token. |
| 403 `forbidden` | Check the `Host` and `Origin` rules above. |
| 404 `not_found` | Check the endpoint path. |
| 405 `method_not_allowed` | Use the method listed for the endpoint. |
| 409 `busy` | A viewer or `/control` owns input, or the input queue cannot fit the batch. Disconnect the owner or wait before trying again. An `applied` field means the session ended after that many records were applied. |
| 411 `length_required` | Include `Content-Length` on `POST /input`. |
| 413 `too_large` | Send no more than 256 input records per batch. |
| 422 `unsupported_input` | The record at zero-based `index` is valid but the desktop cannot apply it, such as an unavailable key or character. |
| 503 `busy` | Another screenshot is running; wait and try again. |
| 503 `screenshot_unavailable` | The screenshot could not be captured or encoded. |
| Screenshot | At most 8 MiB; the connection closes if the request takes over 5 seconds. |
| Input queue | At most 1024 events. |
| Desktop size | Even width from 320 to 1920 and even height from 240 to 1080. |

Error responses are JSON with an `error` field. On an input error with `index`, records before that index were applied. Do not retry a whole batch blindly after an error with `index` or `applied`.

## WebSocket protocol

| Connection | Rule |
| --- | --- |
| `/stream` | Receives video and, when supported, cursor messages. Sends ACKs and input. Requires an `Origin`. |
| `/control` | Receives a control-ready message, then sends input and receives one response per request. Up to 32 replies can be queued. |
| Both | Use the `nsl1` subprotocol and binary messages. One WebSocket message contains one protocol message. Only one input owner is allowed. |

| Header offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 bytes | ASCII `NSL1`. |
| 4 | 1 byte | Version: `1`. |
| 5 | 1 byte | Message type from the table below. |
| 6 | 2 bytes | Flags: zero except frame bit 0, which marks a keyframe. |
| 8 | 4 bytes | Nonzero generation, incremented for each connection. |
| 12 | 4 bytes | Sequence; meaning depends on message type. |
| 16 | 4 bytes | Payload length in bytes. |

| Type | Direction | Payload and sequence |
| ---: | --- | --- |
| 1 | Server to `/stream` | Width and height (2 bytes each), capture time in microseconds (8 bytes), and an H.264 Annex B access unit. Sequence starts at 1 and increases per frame. The first and recovery frames are keyframes with SPS and PPS. |
| 2 | `/stream` to server | Empty payload. ACK each frame in order after drawing it or dropping it for a newer frame; use its generation and sequence. Only the oldest outstanding frame earns credit. |
| 3 | Client to either endpoint | One 16-byte input record. Sequence is zero on `/stream` or a nonzero request ID on `/control`. |
| 4 | Server to `/control` | Desktop width and height, 2 bytes each. Sequence is zero. |
| 5 | Server to `/control` | One status byte: 0 applied, 1 invalid, 2 unsupported. Sequence echoes the request ID. |
| 6 | Server to `/stream` | Width, height, hotspot X, and hotspot Y (2 bytes each), followed by straight-alpha RGBA pixels row by row. Sequence is zero. No ACK is needed. |

| Rule | Detail |
| --- | --- |
| Encoding | All integers are unsigned big-endian except the signed input value. Reject malformed messages and unknown types or versions. |
| Flow control | At most 8 frames and 8 MiB can be in flight. The stream closes after about 3 seconds without ACK progress or when the oldest frame reaches 3 seconds. |
| Frame size | An access unit is at most 8 MiB; the complete message is at most 8,388,640 bytes. Decode frames in order. |
| Counters | Reconnect when the frame sequence reaches 4294967295. If the generation reaches that value, restart the session before connecting again. |
| Cursor | At most 256 by 256 pixels, with the hotspot inside the image. Eight zero bytes restore the local arrow; a transparent image hides the cursor. The cursor does not follow pointer jumps made by the desktop. |
| Disconnect | Held input is released. Reconnecting does not replay requests. |

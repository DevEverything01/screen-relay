Use this page to write a client that streams the desktop, sends input, or takes screenshots without the `relay` CLI or the Node SDK. If you use Node, the [SDK](/docs/sdk) already does all of this.

## Overview

The engine on the VM serves one port (default `8080`):

- `/stream` is a WebSocket that carries video to a viewer and the viewer's input back.
- `/control` is a WebSocket for an agent that sends input and wants a reply for every event.
- `POST /input` sends a batch of input events over plain HTTP.
- `GET /screenshot.png`, `GET /capabilities`, and `GET /metrics` are plain HTTP.

Rules for the binary messages:

- Every integer is unsigned big-endian unless marked signed.
- One binary WebSocket message is one protocol message. Reject text messages, unknown types or versions, bad lengths, and malformed records.
- Read incoming bytes field by field. Never cast them to a native struct.

For how the stream behaves, see [How relay works](/docs/architecture).

## Endpoints

| Route | Purpose |
| --- | --- |
| `GET /`, `GET /index.html`, `GET /viewer.js` | The viewer |
| `WS /stream` | Video, cursor, and human input. Subprotocol `nsl1`. |
| `WS /control` | Agent input. Subprotocol `nsl1`. Exclusive with `/stream`. |
| `POST /input` | A batch of input records over HTTP |
| `GET /screenshot.png` | A fresh PNG of the desktop |
| `GET /capabilities` | Backend, size, and features |
| `GET /metrics` | Stream and resource metrics (JSON) |

One input owner at a time: the viewer on `/stream`, one `/control` connection, or a `POST /input` batch. Anyone else gets `busy`.

## Authentication

| Item | Rule |
| --- | --- |
| `Host` | Must be loopback (`127.0.0.1` or `localhost`, any port) or the authority of `--public`. Otherwise HTTP 403. |
| `Origin` | Optional for native agents. When sent, it must be loopback with a loopback `Host`, or equal the `--public` origin when a token is set. Otherwise HTTP 403. `/stream` requires an `Origin`. |
| Token over HTTP | `Authorization: Bearer TOKEN`. Otherwise HTTP 401. |
| Token over WebSocket | Offer the subprotocols `nsl1` and `bearer.TOKEN`. The server selects `nsl1`. |
| No token | Only for a listener on `127.0.0.1`. The engine refuses a non-loopback bind without a token. |

A token is 64 lowercase hex characters. Never put it in a URL. See [Remote access](/docs/remote-access#tokens).

## Message format

Every WebSocket message starts with a 20-byte header.

| Offset | Size | Field | Meaning |
| ---: | ---: | --- | --- |
| 0 | 4 | Magic | The ASCII bytes `NSL1` |
| 4 | 1 | Version | `1` |
| 5 | 1 | Type | 1 frame, 2 ACK, 3 input, 4 control ready, 5 input response, 6 cursor image |
| 6 | 2 | Flags | Zero, except bit 0 of a frame, which marks a keyframe |
| 8 | 4 | Generation | Starts at 1 and increments per connection. Zero is invalid. |
| 12 | 4 | Sequence | Starts at 1 per generation and increases by one per frame |
| 16 | 4 | Payload length | Bytes after the header |

A new generation invalidates earlier ACKs and queued frames. At sequence 4294967295 the server stops sending frames and the client must reconnect. At generation 4294967295 the server refuses connections until it restarts.

### Frame (type 1, server to viewer)

Payload:

| Offset | Size | Field | Meaning |
| ---: | ---: | --- | --- |
| 0 | 2 | Width | 1 to 1920 |
| 2 | 2 | Height | 1 to 1080 |
| 4 | 8 | Capture time | Microseconds |
| 12 | 1 to 8,388,608 | Access unit | One H.264 Annex B access unit |

The payload length is `12` plus the access unit length, so the largest message is 8,388,640 bytes. The first frame and every recovery frame is a keyframe with SPS and PPS.

Decode every frame in order. Send the ACK when the frame is drawn, or when it is dropped because a newer frame replaced it. A client that draws at the display refresh rate should draw a decoded frame at once when nothing has been drawn since the last refresh, and otherwise queue it for the next one.

### ACK (type 2, viewer to server)

The payload length is zero. The generation and sequence name the oldest frame the server sent and has not yet seen acknowledged. Send one ACK per frame, in order. Only an exact match gives the server credit to send more; stale and future ACKs are ignored. A client that does not ACK stalls, and after about 3 seconds without progress the server closes the stream.

### Cursor image (type 6, server to viewer, `/stream` only)

Sent after the first frame of a generation, and again when the cursor changes. Flags and sequence are zero. It needs no ACK.

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 2 | Width |
| 2 | 2 | Height |
| 4 | 2 | Hotspot X |
| 6 | 2 | Hotspot Y |
| 8 | width x height x 4 | RGBA pixels, straight alpha, row by row |

- The largest image is 256x256, and the hotspot must lie inside it.
- A payload of 8 zero bytes means: show the local arrow.
- A fully transparent image means: show no cursor.
- Only the newest pending image is kept. A new connection gets the current shape.
- The cursor does not follow pointer jumps made by the desktop itself.

### Control ready (type 4, server to client, `/control` only)

Generation is nonzero, sequence is zero, payload is 4 bytes: width (2) and height (2) of the desktop.

### Input response (type 5, server to client, `/control` only)

The sequence is the request ID. The payload is one status byte: 0 applied, 1 invalid, 2 unsupported.

## Input events

An input record is exactly 16 bytes. On `/stream` and in a `/control` message it follows the 20-byte header (type 3). In `POST /input` the records are sent back to back with no header.

| Offset | Size | Field | Meaning |
| ---: | ---: | --- | --- |
| 0 | 1 | Event | 1 key down, 2 key up, 3 pointer move, 4 button down, 5 button up, 6 wheel, 7 release all, 8 text |
| 1 | 1 | Reserved | Zero |
| 2 | 2 | Code | Key: HID usage. Button: 1 to 3. Move: 0. Wheel: axis, 0 vertical, 1 horizontal. |
| 4 | 4 | Value | Signed. Wheel: delta. Text: codepoint. Otherwise zero. |
| 8 | 2 | X | 0 to 65535, across the full desktop width |
| 10 | 2 | Y | 0 to 65535, across the full desktop height |
| 12 | 2 | Button mask | Low 5 bits only |
| 14 | 2 | Modifier mask | HID modifier bits 0 to 7 |

In the message header, the sequence is zero on `/stream`, and a nonzero request ID on `/control` that the reply echoes. Use the current generation.

Rules:

- Key codes are HID usages from 0x00 to 0xE7. Larger values are invalid. A usage in range that the display has no key for returns status 2 (unsupported).
- Key codes name physical keys, so the keyboard layout of the desktop decides the character.
- Wheel delta is in steps of 120 with a magnitude of at most 1200.
- Release all needs code, value, and both masks to be zero. Coordinates are ignored.
- Repeated key down or button down for something already held, and repeated releases, are ignored. The held set is the source of truth.
- A `/control` message may arrive in fragments; the engine accumulates up to 36 bytes.

### Text events

A text event types one character, whatever the keyboard layout.

- Code is 0, value is one Unicode scalar value from 1 to 0x10FFFF, excluding 0xD800 to 0xDFFF. Both masks are zero and X and Y are ignored.
- A text event never changes the held keys. Modifiers you hold, such as Shift or Ctrl, are lifted for the character and pressed again right after, so they never change what is typed.
- Value 0x0A types the Return key and 0x09 types the Tab key, so applications see the named keys.
- Status 2 (unsupported) means the desktop could not type the character.
- On X11, relay uses the layout's own key when it is available for the character. Otherwise, it uses a spare key temporarily bound to the character, such as for CJK on `us`. The binding stays valid for at least 50 ms, and relay uses up to 16 spare keys before reusing one. An application that stays frozen longer than 50 ms can miss characters typed during the freeze if their spare keys are reused. This is a limit of X11, not of relay.
- With no spare key left at all, the character is unsupported.

## /control: agent input over WebSocket

1. Connect to `/control` with the `nsl1` subprotocol and your token. No video starts.
2. The server sends a control ready message (type 4).
3. Send input requests (type 3). Each gets one response (type 5) with the same sequence. The reply is written after the desktop has applied the input, so a client that waits for it before the next request is paced by the desktop.
4. At most 32 replies are queued. A protocol violation closes the connection and releases held input.

Reconnecting never replays requests. Applied means the desktop received the input, not that the application reacted.

## POST /input

Sends 1 to 256 input records, 16 bytes each, in the format above with no WebSocket header. `Content-Length` is required. Send the bearer token.

```sh
printf '\x01\x00\x00\x04\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00' |
  curl -s -X POST http://127.0.0.1:8080/input \
    -H "Authorization: Bearer $TOKEN" \
    --data-binary @-
```

```json
{"applied":1}
```

| Status | Body | Meaning |
| --- | --- | --- |
| 200 | `{"applied":N}` | Every record was applied. |
| 400 | `{"error":"invalid_input","index":I}` | Record `I` is invalid. Records before it were applied. Without `index` when the body is empty or not a multiple of 16 bytes. |
| 401 | `{"error":"unauthorized"}` | Missing or wrong token. |
| 403 | `{"error":"forbidden"}` | `Host` or `Origin` rejected. |
| 409 | `{"error":"busy"}` | A viewer or `/control` owns input, or the input queue already holds 1024 events. Nothing was applied. |
| 409 | `{"error":"busy","applied":N}` | The session ended after the batch started. `N` records were applied and the rest were dropped. |
| 411 | `{"error":"length_required"}` | No `Content-Length`. |
| 413 | `{"error":"too_large"}` | More than 256 records. |
| 422 | `{"error":"unsupported_input","index":I}` | Record `I` is valid but cannot be done, such as a key the display lacks or a character it cannot type. Records before it were applied. |

- Records are applied in order and stop at the first failure.
- The response is written after the desktop has applied the records, so a long batch of text returns when its last character is typed.
- Keys and buttons held by the batch are released when it ends or fails.
- Never retry a whole batch blindly: on `busy` with `applied`, or on a 400 or 422 with `index`, some records already ran.
- The server never retries on its own.

## GET /screenshot.png

Returns a fresh PNG of the desktop, whoever owns input, including while a viewer is connected. It does not include the mouse cursor.

```sh
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/screenshot.png -o screen.png
```

One screenshot runs at a time. A second request while one is running gets HTTP 503 with a JSON error. The response must complete within 5 seconds and is at most 8 MiB.

## GET /capabilities

```sh
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/capabilities
```

```json
{"version":1,"backend":"x11","width":1280,"height":720,"fps":60,"input":{"keyboard":true,"pointer":true,"buttons":true,"wheel":true},"screenshot":"/screenshot.png","control":"/control","wayland":false,"max_input_pending":32,"cursor":true,"input_endpoint":"/input","max_input_batch":256,"audio":false,"clipboard":false,"resize":false,"ime":false}
```

| Field | Meaning |
| --- | --- |
| `fps` | The configured capture frame rate |
| `cursor` | Whether `/stream` sends cursor images |
| `max_input_batch` | The most records one `POST /input` accepts |
| `max_input_pending` | The most `/control` replies that can be queued |
| `audio`, `clipboard`, `resize`, `ime` | Features the engine does not offer today |

## GET /metrics

Returns uncached JSON for the current stream and the engine's resource use.

```sh
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/metrics
```

```json
{"usage_usec":1002503,"memory_current":130478080,"inactive_file":98304,"inflight_frames":0,"inflight_bytes":0,"window_frames":1,"target_bitrate_bps":8000000,"ack_rtt_ms":0.000000,"oldest_frame_ms":0.000000,"frames_acked":0,"frames_encoded":0,"observed_busy_goodput_bps":0.000000,"max_inflight_frames":8,"max_inflight_bytes":8388608,"max_frame_bytes":8388608,"admission_age_ms":250,"no_ack_timeout_ms":3000,"max_frame_age_ms":3000}
```

| Field | Meaning |
| --- | --- |
| `usage_usec` | CPU time used, in cumulative microseconds |
| `memory_current`, `inactive_file` | Memory in bytes, from the cgroup |
| `inflight_frames`, `inflight_bytes` | Frames sent and not yet acknowledged |
| `window_frames` | How many frames the engine allows in flight now |
| `target_bitrate_bps` | The bitrate the encoder is aiming for |
| `ack_rtt_ms` | Smoothed time from sending a frame to its ACK. It includes decoding and drawing, so it is more than network round trip. |
| `oldest_frame_ms` | Age of the oldest unacknowledged frame |
| `frames_acked`, `frames_encoded` | Counts for the current stream |
| `observed_busy_goodput_bps` | Measured delivery rate while the link was busy |
| `max_inflight_frames`, `max_inflight_bytes`, `max_frame_bytes` | Limits on frames in flight and on one frame |
| `admission_age_ms` | Age of the oldest unacknowledged frame at which the engine stops capturing new frames |
| `no_ack_timeout_ms`, `max_frame_age_ms` | How long without an ACK, or how old a frame, before the stream is closed |

The flow fields cover the current connection only. If the VM has no cgroup v2 data, the response is still 200 with `"resources_available": false` and `usage_usec`, `memory_current`, and `inactive_file` are `null`.

## Limits

| Item | Value |
| --- | --- |
| Desktop size | Even width 320 to 1920, even height 240 to 1080 |
| Frame message | 8,388,640 bytes |
| Frames in flight | At most 8 frames and 8 MiB |
| Input record | 16 bytes |
| `POST /input` batch | 256 records |
| Input queue | 1024 events |
| `/control` replies queued | 32 |
| Cursor image | 256x256 |
| No ACK progress | Stream closed after about 3 seconds |

The bundled viewer waits up to 5 seconds for its first frame and decoder. After a drop it reconnects after 1, 2, 4, 8, and 8 seconds, then stops unless a frame was drawn. A hidden tab pauses the stream, and returning to it reconnects with a new generation and a keyframe. A client of your own can follow the same pattern.

The engine and the viewer ship together. A viewer that only knows frames (type 1) does not support cursor images.

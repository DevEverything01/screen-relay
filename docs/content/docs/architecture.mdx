title: How relay works

Relay runs one process, the engine, on a Linux VM. It captures the desktop, encodes it as H.264 video, sends it to a browser over one WebSocket, and applies input from that browser or from an agent.

<Diagram name="architecture" title="Relay architecture: the capture and encode pipeline in a Linux VM, the browser viewer, and the input path" aspectRatio="720 / 480" />

The same flow in text:

```text
Linux VM
  display -> capture -> H.264 encode -> /stream WebSocket -> browser viewer

viewer input over /stream
agent input over /input (HTTP) or /control (WebSocket)
  -> input checks -> keyboard and mouse input -> display
```

## What runs where

| Part | What it is |
| --- | --- |
| VM | The Linux machine, container, or sandbox that runs `relay up`. |
| Session | One desktop started by `relay up`, named with `--name` (default `default`). |
| Display | The screen relay captures: a virtual one it starts, or an existing X11 display or Wayland compositor you attach to. |
| Desktop | What runs on the display: XFCE, a command you choose, or `none` for a bare screen. |
| Engine | The relay process on the VM. |
| Viewer | The browser page that shows the desktop and returns your keyboard and mouse. |
| Agent | A program that controls the desktop from the CLI, the SDK, or the API, on the VM or [another machine](/docs/remote-access). |

## From the desktop to the browser

The display reports which regions changed, and the engine captures only those. When the screen is still, relay refines the last frame instead of resending it. `relay screenshot` reads the display directly, so it works with or without a viewer.

Frames travel over one WebSocket, `/stream`, encoded as H.264 for low delay, and the first frame of a connection is a full picture. On X11 the cursor is a separate image, so it moves without waiting for the video. On Wayland the viewer draws its own arrow ([Wayland](/docs/wayland#limits)).

A hidden tab pauses the stream.

## Adapting to the network

The engine sends frames only as fast as the viewer acknowledges them.

- A slow link backs off. The bitrate drops, fewer frames stay in flight, and capture pauses while the engine waits, so the desktop does not fall behind.
- A still screen gets sharper. About 150 ms after the picture stops changing, relay refines it at higher quality while the link is idle.
- A stalled link ends the stream. After about 3 seconds without an acknowledgement, the engine closes it and the viewer reconnects.

The bitrate starts at 8 Mbps and moves between 1 and 40 Mbps, and the frame rate is 10 to 60 (60 by default). Set both in [Configuration](/docs/configuration). Live numbers are in `GET /metrics`; see [HTTP API](/docs/protocol#endpoints).

## From the browser or an agent back to the desktop

| Source | Path |
| --- | --- |
| Viewer | Keyboard and mouse events over the same `/stream` WebSocket. |
| Agent over HTTP | Batches from the CLI client commands and the SDK to `POST /input`. |
| Agent over WebSocket | One event at a time on a long-lived `/control` connection, with a reply for each. |

The engine checks every event and injects it into the display as real keyboard and mouse input. An agent's reply comes after the display has the input, so an agent that waits for it is paced by the desktop.

### One input owner at a time

Only one of the viewer, `/control`, and `/input` can send input at once, and a second one gets a `busy` error. When the owner disconnects, times out, or the tab loses focus, every key and mouse button it held is released.

Typed text uses the desktop's keyboard layout (`us` by default); see [HTTP API](/docs/protocol#input-events) for characters it lacks.

## Limits you will notice

| Limit | What it means |
| --- | --- |
| Resolution | 1280x720 by default. Width even, 320 to 1920; height even, 240 to 1080. |
| Slow links | Above about 200 ms of delay the stream keeps lowering its quality. Move the VM closer, or lower `stream.bitrate.max`. |
| Video only | No audio, clipboard sync, or live resize. Change the resolution in [Configuration](/docs/configuration) or select another Wayland output, then restart relay. |
| Browser | Needs H.264 (WebCodecs) in current Chrome, Edge, or Safari. |
| Colored text | Color detail is shared between neighboring pixels, so fine colored text looks softer. |
| Failure | Three capture failures in a row end the session. `relay logs` shows why. |

See [Troubleshooting](/docs/troubleshooting) when something is slow or stuck.

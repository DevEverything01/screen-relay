title: How streaming works
description: How relay gets each frame from the desktop to your browser, and how it adapts the frame rate, bitrate, and smoothness to your connection.
---

Relay streams frames from the VM to your browser and uses what the browser reports back to match the stream to your connection. This page explains that loop so you know which settings change what you see and what to expect on a slow, long, or unsteady link.

## The streaming loop

<Diagram name="streaming-loop" title="How a frame travels from the desktop to the browser and how feedback returns" aspectRatio="720 / 368" />

The same flow in text:

```text
Linux VM: Desktop -> relay engine (paints)
relay engine -> Viewer in the browser (frames)
Viewer -> Acknowledgement (after showing)
Acknowledgement -> Rate control on the VM (wait time)
Rate control -> relay engine (bitrate, frames on the way, pause)
```

Each frame takes this path:

1. An app paints the desktop on the VM.
2. The engine captures the screen only when it changed, and only the part that changed.
3. The engine encodes the frame at the current bitrate.
4. The frame travels to the browser.
5. The viewer decodes the frame and shows it on a steady clock. When frames arrive unevenly, it holds each one briefly so motion stays even.
6. After showing a frame, the viewer sends an acknowledgement that says how long the frame waited in the viewer.

The engine uses the acknowledgements to adapt:

1. It learns the link's normal round trip and whether a queue is building in the network. The time frames wait in the viewer is taken out, so a slow browser is not mistaken for a slow network.
2. It sets how many frames can be on the way at once, sized to the link's round trip so a long link does not lose frames.
3. It pauses capture while a queue keeps standing, so frames do not pile up behind it.
4. It raises the bitrate while the link is clear and lowers it when a queue stands in the network. The bitrate stays between `stream.bitrate.min` and `stream.bitrate.max`.

## Frame rate

The stream runs at up to `stream.fps` frames per second, from 10 to 120. The default is 60. An idle desktop sends no frames, because the engine only captures when the screen changes.

The compositor in relay's own XFCE desktop repaints at most 60 times a second. When `stream.fps` is above 60, relay turns it off so apps can update the screen faster, which also removes window shadows and transparency. Set `display.compositor` to `on` or `off` to decide this yourself; see [Configuration](/docs/configuration). A desktop you attach to with `--display` keeps its own settings.

## Picture quality on a slow or long link

The bitrate starts at `stream.bitrate.start` (8 Mbps by default). While the link is clear, relay raises it toward `stream.bitrate.max` (40 Mbps). When a queue stands in the network, it lowers the bitrate toward `stream.bitrate.min` (1 Mbps), which makes the picture softer but keeps motion current.

On a long link, the engine allows more frames on the way at once, based on the link's round trip, so the stream keeps its frame rate instead of waiting for each acknowledgement.

See [Configuration](/docs/configuration#keys) for the bitrate keys and their defaults.

## Smoothness on an unsteady link

When frames arrive at uneven intervals, the viewer holds each frame for a short time before it shows it, so motion stays even. The hold is at most 100 ms and is near zero on a clean link. It adds to the delay between an action on the VM and the screen, so on a very unsteady link you trade up to 100 ms of latency for smoother motion.

## When the link stalls

If the engine has frames outstanding and receives no acknowledgement for about 3 seconds, it closes the stream. The viewer reconnects on its own, up to five times with growing delays, and then shows a message asking you to reconnect manually. Reloading the page starts a new stream.

## Inside the engine

This section is for readers who want to see how the engine decides. You do not need it to run relay.

### One frame inside the engine

<Diagram name="engine-pipeline" title="The stages one frame goes through inside the engine" aspectRatio="720 / 416" />

The same flow in text:

```text
Wait (for a screen change) -> Admit (change)
Admit (takes a frame only if fewer frames are on the way than allowed and capture is not paused) -> Pace (allowed)
Pace (keeps capture at the configured frame rate, with a reserve of two frames) -> Capture (on pace)
Capture (reads only the changed region, converts it block by block, marks unchanged blocks, no change means no frame) -> Encode (pixels)
Encode (at the current bitrate, skips marked blocks, a keyframe starts a session and follows a recovery) -> Send (frame)
Send (queues the frame to the viewer with its capture time and sequence number)
```

1. **Wait.** Nothing is captured while the screen is still. The engine waits for the desktop to report a change.
2. **Admit.** The engine takes a frame only if fewer frames are on the way than the stream allows and capture is not paused.
3. **Pace.** A rate limiter keeps capture at the configured frame rate. It keeps a reserve of two frames, so a short burst of changes is not delayed.
4. **Capture.** The engine reads only the region of the screen that changed.
5. **Convert and compare.** The engine converts the region for the encoder block by block, and marks the blocks whose pixels did not change so the encoder skips them. If nothing changed, it sends no frame.
6. **Encode.** The engine encodes at the current bitrate. The first frame of a session, and the first frame after a recovery, is a keyframe that the viewer can start from. When the screen goes quiet, the engine sends a few refinement frames that sharpen the last picture, then stops.
7. **Send.** The engine queues the frame to the viewer with its capture time and a sequence number.

### How acknowledgements become decisions

<Diagram name="engine-flow" title="How acknowledgements become the frame window, the pause, and the bitrate" aspectRatio="720 / 536" />

The same flow in text:

```text
Acknowledgement (total time since capture and its wait in the viewer) -> Recent delays (delays)
Acknowledgement -> Standing queue (delays)
Recent delays (shortest over 10 s is the normal delay; longest sizes the window) -> Standing queue (its base)
Recent delays -> Frame window (largest)
Standing queue (smallest delay above the base over one round trip) -> Pause (all of it)
Standing queue -> Bitrate (network part)
Safety limits: at most 3 s of frames and 8 MiB on the way; the stream closes after 3 s without progress
```

Each acknowledgement gives the engine two numbers: the time from capture to acknowledgement, and how long the frame waited in the viewer.

- **Base delay.** The shortest capture-to-acknowledgement time over the last 10 seconds is the link's normal delay.
- **Standing queue.** The smallest delay above the base over one round trip. A single late burst leaves it at zero, because some frames in that round trip still arrive on time. Real congestion raises it.

The engine turns these into three decisions:

- **Frame window.** How many frames can be on the way is sized from the largest recent delay, plus two frames. Before the first acknowledgement, one frame is allowed.
- **Pause.** Capture pauses when the standing queue, viewer wait included, reaches the base delay plus two frame intervals.
- **Bitrate.** The bitrate drops by a quarter when the network part of the standing queue is high, which means the queue with the viewer's wait taken out. It rises 10% a second while the queue is clear. It always stays between `stream.bitrate.min` and `stream.bitrate.max`, and it is never cut before the first acknowledgement.

Two safety limits apply regardless: at most 3 seconds of frames and 8 MiB can be on the way, and the stream closes after about 3 seconds without progress.

When the engine can read the operating system's TCP statistics (on Linux, over a direct connection), it takes the round trip and the bitrate from those. Behind a proxy, and on macOS and Windows, it uses the acknowledgements as described above.
